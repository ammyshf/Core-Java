The Mutex Misconception
What synchronized ACTUALLY locks — it’s NOT the class, method, or block
⚠️
Common Wrong Beliefs
“synchronized locks the class” — Wrong.
“synchronized locks the method” — Wrong.
“synchronized locks the block” — Wrong.

Truth: synchronized locks an OBJECT. The method or block is just the scope — how long that lock is held.
🔑
Think of a bathroom key. The OBJECT is the key itself. The method/block is how long you hold the key. Method-level = you keep the key from entering the building to leaving. Block-level = you grab the key only when you enter the bathroom and return it immediately after.
What ACTUALLY gets locked in each case
Instance Method
synchronized void method()
Lock = this (the calling instance). Same as synchronized(this) { } wrapping the whole method. Each object has its own lock.
Static Method
static synchronized void method()
Lock = ClassName.class (the Class object). One lock for the entire JVM, regardless of how many instances exist.
Block on this
synchronized(this) { ... }
Lock = this instance, but held only for the block. Code before and after runs freely without any lock.
Block on Custom Object
synchronized(lockObj) { ... }
Lock = any object you choose. Most flexible! Use different lock objects for different resources → maximum parallelism.
💡
The Golden Rule
Two threads using the SAME object as lock → only one can enter. Two threads using DIFFERENT objects as lock → both run simultaneously. The object IS the lock.

3
wait() / notify() / notifyAll()
Inter-thread communication — everything is about the OBJECT
💡
Key Insight
wait(), notify(), notifyAll() are methods of Object class — not Thread class. Every Java object has a monitor. The lock is on an object. wait/notify is also on the same object. Threads communicate THROUGH the object’s monitor.
What happens when a Thread calls wait()
1
RELEASES the lock — This is crucial! Without releasing, no other thread could ever enter the synchronized block and call notify().
2
Moves to WAIT SET — Thread goes to sleep inside the monitor’s wait set. It’s completely dormant.
3
When notified → moves to ENTRY SET — Must re-acquire the lock before it can continue executing from the line after wait().
notify()
Wake ONE random thread
Moves one thread from Wait Set to Entry Set. Does NOT release lock. The woken thread still must wait for the lock to become available.
notifyAll()
Wake ALL threads
Moves all threads from Wait Set to Entry Set. They all compete for the lock — only ONE wins. Rest go back to BLOCKED state in Entry Set.
⚠️
wait() vs sleep() — THE Key Difference
wait(): RELEASES the lock, must be inside synchronized, used for inter-thread communication.
sleep(): Does NOT release the lock, doesn’t need synchronized, just pauses the thread.

Why while-loop and not if? Because of spurious wakeups (thread can wake without notify) and notifyAll() (multiple threads wake but only one can act).
Template: Producer-Consumer with wait/notify
public synchronized void produce(int item) throws InterruptedException {
while (buffer.size() == capacity)
while, NOT if (spurious wakeup!)
wait();
Releases lock + sleeps
buffer.add(item);
Critical section
notifyAll();
Wake waiting consumers
}
4
ReentrantLock
Explicit lock with superpowers: tryLock, timeout, fairness, multiple Conditions
🔧
synchronized = automatic car door lock (simple, JVM manages everything). ReentrantLock = manual lock with a physical key — you decide when to lock, when to unlock, you can try the lock, set a timeout, and choose fairness.
4 Superpowers that synchronized doesn’t have
Power 1: tryLock()
Try Without Blocking
Returns true/false immediately. Can’t get lock? Do something else instead of blocking forever. Prevents thread starvation.
Power 2: tryLock(timeout)
Wait With Timeout
Wait max N seconds for the lock. If still blocked, give up gracefully. Critical for trading systems.
Power 3: lockInterruptibly()
Can Be Interrupted
A thread waiting for the lock can be interrupted and cleanly exit. synchronized ignores interrupt() while BLOCKED.
Power 4: Fairness
First Come, First Served
new ReentrantLock(true) guarantees FIFO order. Longest-waiting thread gets lock first. synchronized has no fairness.
🔄
What does “Reentrant” mean?
Same thread can acquire the same lock multiple times without deadlocking itself. Lock keeps a hold count: lock() increments it, unlock() decrements it. Truly released when count reaches 0. Note: synchronized is also reentrant!
Template: ReentrantLock with try-finally
private final ReentrantLock lock = new ReentrantLock();
public void criticalSection() {
lock.lock();
Acquire lock
try {
// your protected code here
Critical section
} finally {
lock.unlock();
MUST unlock in finally!
}
}
Condition: Multiple Wait Sets (synchronized has only ONE)
Condition notFull = lock.newCondition();
Producers wait here
Condition notEmpty = lock.newCondition();
Consumers wait here
notFull.await();
equivalent to wait()
notEmpty.signal();
equivalent to notify() — targeted!
notEmpty.signalAll();
equivalent to notifyAll()

Template: ReadWriteLock
ReadWriteLock rwLock = new ReentrantReadWriteLock();
Lock readLock = rwLock.readLock();
Shared lock (many readers)
Lock writeLock = rwLock.writeLock();
Exclusive lock (one writer)
double getPrice() {
readLock.lock();
Multiple threads can read

StampedLock (Java 8+) — Even Faster Reads
Optimistic Read
Lock-free reading
Gets a stamp, reads data, then validates. If no writer intervened, the read was valid. Zero contention for reads! Falls back to a real read lock if validation fails.
Trade-off
Not reentrant!
StampedLock is NOT reentrant. Calling lock twice from same thread → deadlock! Not Condition-compatible either. Use only when optimistic reads give a clear benefit.
Template: StampedLock Optimistic Read
StampedLock sl = new StampedLock();

double getPrice() {
    long stamp = sl.tryOptimisticRead();   // No lock! Just a stamp
    double p = price;                      // Read optimistically
    if (!sl.validate(stamp)) {              // Did a writer intervene?
        stamp = sl.readLock();              // Fallback: real read lock
        try { p = price; }
        finally { sl.unlockRead(stamp); }
    }
    return p;
}
6
Semaphore
Allow N threads simultaneously — like a parking lot with N spaces
🅿️
synchronized / ReentrantLock = bathroom with 1 key (1 thread at a time). Semaphore(N) = parking lot with N spaces. When all spaces are taken, new cars wait. When a car leaves (release), the next car enters.
Semaphore(3) — 3 Permits Available
T-1 🚗
SLOT 1
T-2 🚗
SLOT 2
T-3 🚗
SLOT 3
T-4 🚗 WAITING
FULL!
permits = 0 → T-4 blocked at acquire(). When T-2 calls release() → T-4 enters.
⚠️
Semaphore(1) is NOT the same as a Mutex!
Mutex / ReentrantLock: Only the thread that locked can unlock. Is reentrant. Has ownership.
Semaphore(1): ANY thread can release! NOT reentrant (same thread acquires twice = deadlock). No ownership concept.
Template: Semaphore (DB Connection Pool)
Semaphore sem = new Semaphore(5);  // max 5 concurrent connections

public void executeQuery(String query) throws InterruptedException {
    sem.acquire();                      // get a permit (or block if 0)
    try {
        runQuery(query);                // max 5 threads here at once
    } finally {
        sem.release();                  // return the permit
    }
}

CountDownLatch
Wait for N events to complete — one-time gate that opens when count reaches zero
🚀
Like a rocket launch countdown. Set count to 3. Three systems report ready (countDown). When count hits 0, the rocket launches (await returns). One-time use only — cannot be reset.
CountDownLatch(3) — Flow
Service-A
countDown()
Service-B
countDown()
Service-C
countDown()
→
count = 0
GATE OPENS!
→
Main Thread
await() returns!
Template: CountDownLatch
CountDownLatch latch = new CountDownLatch(3);  // gate closed, count = 3

// Each worker thread:
void workerTask() {
    doWork();
    latch.countDown();    // count-- (3 → 2 → 1 → 0)
}

// Main thread:
latch.await();            // blocks until count = 0
System.out.println("All services ready! Launching...");
8
CyclicBarrier
All threads wait for each other — a reusable meeting point
🏃
Like friends meeting at a restaurant. Everyone arrives at different times, but nobody starts eating until all 4 arrive. Once all arrive, everyone eats. Then they can agree to meet again next week — it’s reusable!
CountDownLatch
N threads signal, 1 thread waits
Workers do countDown(), main thread does await(). One-time use. Cannot be reset. Event-based: “wait for N events”.
CyclicBarrier
All N threads wait for each other
Every thread calls await(). All block until N arrive. Reusable! Auto-resets after tripping. Rendezvous: “wait for each other”.
CyclicBarrier(4) — All Wait for Each Other
Thread-1
work
await()... waiting for others
🎉 continue!
Thread-2
work...
await()... waiting
🎉 continue!
Thread-3
work......
await()
🎉 continue!
Thread-4
work............
✓
🎉 continue!
All 4 arrive → barrier trips → everyone continues! Barrier auto-resets for next round.
Template: CyclicBarrier
CyclicBarrier barrier = new CyclicBarrier(4, () -> {
    System.out.println("All 4 arrived! Proceeding...");
});

// Each of the 4 threads:
void task() throws Exception {
    doPhase1();
    barrier.await();     // block until all 4 arrive
    doPhase2();           // everyone proceeds together!
    barrier.await();     // reusable! wait again for phase 2
}

Templates & Cheat Sheet
Copy-paste templates & decision framework for any concurrency problem
Pattern Recognition: Which tool for which problem?
When you see this...Reach for this tool
“Execute in ORDER”CountDownLatch or Semaphore(0)
“ALTERNATE between threads”Two Semaphores (ping-pong pattern)
“LIMIT to N concurrent”Semaphore(N)
“Wait for ALL to arrive”CyclicBarrier(N)
“Wait for N events”CountDownLatch(N)
“Producer-Consumer”BlockingQueue or ReentrantLock + Condition
“Many readers, 1 writer”ReadWriteLock or StampedLock
“Prevent deadlock”Lock ordering or tryLock(timeout)
“Thread-safe singleton”volatile + double-checked locking / Bill Pugh / Enum
Template: Print FooBar Alternately (LC 1115)
Semaphore fooSem = new Semaphore(1);  // foo goes first
Semaphore barSem = new Semaphore(0);  // bar waits

void foo(Runnable printFoo) throws InterruptedException {
    for (int i = 0; i < n; i++) {
        fooSem.acquire();     // wait for my turn
        printFoo.run();
        barSem.release();     // signal bar to go
    }
}
void bar(Runnable printBar) throws InterruptedException {
    for (int i = 0; i < n; i++) {
        barSem.acquire();     // wait for my turn
        printBar.run();
        fooSem.release();     // signal foo to go
    }
}
Template: Producer-Consumer (ReentrantLock + Condition)
ReentrantLock lock   = new ReentrantLock();
Condition notFull    = lock.newCondition();
Condition notEmpty   = lock.newCondition();
Queue<T> buffer      = new LinkedList<>();

void produce(T item) throws InterruptedException {
    lock.lock();
    try {
        while (buffer.size() == capacity)
            notFull.await();       // only producers wait here
        buffer.add(item);
        notEmpty.signal();      // wake exactly ONE consumer
    } finally { lock.unlock(); }
}

T consume() throws InterruptedException {
    lock.lock();
    try {
        while (buffer.isEmpty())
            notEmpty.await();      // only consumers wait here
        T item = buffer.poll();
        notFull.signal();       // wake exactly ONE producer
        return item;
    } finally { lock.unlock(); }
}
Template: Thread-Safe Singleton (3 approaches)
// 1. Double-Checked Locking (volatile + synchronized)
class Singleton {
    private static volatile Singleton instance;
    public static Singleton getInstance() {
        if (instance == null) {                  // 1st check (no lock)
            synchronized (Singleton.class) {
                if (instance == null)              // 2nd check (with lock)
                    instance = new Singleton();
            }
        }
        return instance;
    }
}

// 2. Bill Pugh (inner static class — lazy, thread-safe by JVM)
class Singleton {
    private static class Holder {
        static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton getInstance() { return Holder.INSTANCE; }
}

// 3. Enum (simplest, reflection-safe, serialization-safe)
enum Singleton { INSTANCE; }

Deadlock: 4 Conditions (ALL must be true)
Condition 1
Mutual Exclusion
Resource held exclusively by one thread at a time.
Condition 2
Hold and Wait
Hold one lock while waiting for another.
Condition 3
No Preemption
Can’t forcibly take a lock from another thread.
Prevention
Break ANY one condition
Lock ordering (breaks circular wait), tryLock(timeout) (breaks hold-and-wait), Semaphore limit (fewer participants).

Recently Asked Questions in DSA Rounds
Real concurrency problems asked in interviews — framed as DSA-style questions
💡
How to Approach These
These are NOT just theory — interviewers expect you to code them live using Java concurrency primitives. Identify the coordination pattern first, then pick the right tool (Semaphore, ReentrantLock, wait/notify, etc.).
Question 1 — Matrix Print (Multi-threaded)
Amazon • Goldman Sachs • Morgan Stanley
Print an M×N Matrix Row-by-Row Using N Threads
Given an M×N matrix, you have N threads (one per column).
Thread-0 prints column 0 of every row, Thread-1 prints column 1 of every row, and so on.

Constraint: Output must be in order — row 0 fully printed before row 1 starts.
Within a row, columns must print left-to-right: Thread-0 → Thread-1 → … → Thread-(N-1).

Example: 
Matrix:              Expected Output:
 1  2  3              Thread-0: 1
 4  5  6              Thread-1: 2
 7  8  9              Thread-2: 3
                      Thread-0: 4
                      Thread-1: 5
                      Thread-2: 6
                      Thread-0: 7
                      Thread-1: 8
                      Thread-2: 9
Approach Hint
Semaphore Chain
Each thread has a Semaphore. After Thread-i prints, it releases Thread-(i+1) % N’s semaphore. Only Thread-0’s semaphore starts with 1 permit.
Alternate Approach
CyclicBarrier + Turn Variable
Use a shared AtomicInteger turn. Each thread spins/waits until turn == myId, prints, increments turn. CyclicBarrier at end of each row.
Question 2 — Producer-Consumer (Bounded Buffer)
Morgan Stanley • Flipkart • Uber • Google
Implement a Thread-Safe Bounded Buffer (BlockingQueue)
Implement a bounded buffer of size K that supports:
• produce(item) — blocks if buffer is full
• consume() — blocks if buffer is empty

Multiple producers and multiple consumers must work concurrently without data loss or deadlock.

Variants asked:
Variant A
Using wait() / notify()
Classic approach — synchronized block on the buffer, while-loop guard for spurious wakeups, notifyAll() after produce/consume.
Variant B
Using ReentrantLock + Condition
Two conditions: notFull and notEmpty. Signal the other condition after each operation. More precise than notifyAll.
Variant C
Using Semaphore
Three semaphores: empty(K), full(0), mutex(1). Producer acquires empty, acquires mutex, inserts, releases mutex, releases full.
Follow-up
Make it Lock-Free
Use AtomicInteger head/tail pointers on a circular array. CAS-based insert/remove. Asked at Google/Uber.
Question 3 — Dining Philosophers (LC 1226)
Microsoft • Amazon • Morgan Stanley • LeetCode 1226
5 Philosophers, 5 Forks — No Deadlock, No Starvation
5 philosophers sit around a circular table. Each needs both adjacent forks to eat.
Implement wantsToEat(id, pickLeftFork, pickRightFork, eat, putLeftFork, putRightFork)

Must avoid: Deadlock (all hold left fork, wait for right) and Starvation (a philosopher never eats).

Classic DSA Problem — 3 approaches expected:
Approach 1
Resource Ordering
Always pick the lower-numbered fork first. Breaks circular wait. Simple and elegant — preferred answer in interviews.
Approach 2
Semaphore Limit (N-1)
Allow at most 4 philosophers to attempt eating simultaneously using a Semaphore(4). Guarantees at least one can get both forks.
Approach 3
Odd-Even Strategy
Odd philosophers pick left first, even pick right first. Breaks the symmetry that causes circular wait.
Follow-up
Prove Deadlock-Freedom
Interviewer will ask: “Why does this prevent deadlock?” Map your solution to the 4 deadlock conditions and show which one you break.
Question 4 — Print FooBar Alternately (LC 1115)
Amazon • Microsoft • LeetCode 1115
Two Threads Print “foobar” N Times in Strict Alternation
Thread A calls foo(), Thread B calls bar(). Output must be: foobarfoobarfoobar… (N times).

Constraint: foo() always runs before bar() in each iteration — strict ordering.

Variants also asked:
• Print Zero Even Odd (LC 1116) — 3 threads, output: 0102030405
• Print in Order (LC 1114) — 3 threads, guarantee first() → second() → third()
• Building H2O (LC 1117) — group threads as 2H + 1O before releasing
Approach 1
Two Semaphores
fooSem(1) and barSem(0). foo() acquires fooSem, prints, releases barSem. bar() acquires barSem, prints, releases fooSem.
Approach 2
ReentrantLock + Condition
Shared boolean fooTurn = true. foo() waits while !fooTurn, prints, sets fooTurn=false, signals. Mirror for bar().
Question 5 — Design a Read-Write Lock from Scratch
Morgan Stanley • Goldman Sachs • JP Morgan
Implement ReadWriteLock Using Only synchronized / wait-notify
Build a lock that allows:
• Multiple readers concurrently (shared access)
• Only one writer at a time (exclusive access)
• No reader while writer is active and vice versa

Implement: acquireReadLock(), releaseReadLock(), acquireWriteLock(), releaseWriteLock()

Follow-ups:
• How do you prevent writer starvation? (writers keep waiting because readers keep arriving)
• How would you add lock downgrading? (writer → reader without releasing)
• Compare with Java’s ReentrantReadWriteLock and StampedLock
Key Insight
Track Active Readers + Writer Flag
Maintain int readersCount and boolean writerActive. Readers wait if writerActive. Writer waits if readersCount > 0 or writerActive.
Starvation Fix
Add writerWaiting Flag
When a writer is waiting, new readers must also wait. This prevents the “endless reader stream” problem.
