CONCEPT 1
synchronized locks the ???
Let’s kill the misconception once and for all.
❌ What most people think
“It locks the method”
“It locks the class”
“It locks the code block”
All three are WRONG.
✅ What it actually does
synchronized acquires a
mutex lock on an OBJECT
• Method-level: locks this (the instance)
• Static method: locks ClassName.class
• Block-level: locks whatever object you pass
SAME OBJECT = SAME LOCK = BLOCKED
Thread A
methodA()
both lock
↓
🔒
this
same object
both lock
↓
Thread B
methodB()
⚠ Thread B is BLOCKED even though it calls a DIFFERENT method!
FIX: USE DIFFERENT LOCK OBJECTS
private final Object lockA = new Object(); private final Object lockB = new Object(); void methodA() { synchronized(lockA) { ... } } // independent! void methodB() { synchronized(lockB) { ... } } // runs in parallel

THREE GOLDEN RULES
Rule 1
wait() / notify() MUST be inside synchronized
Rule 2
Always while(!condition) not if — spurious wakeups!
Rule 3
wait() releases the lock. Re-acquires on wakeup.
synchronized(lock) { while(!condition) { // while, NOT if! lock.wait(); // releases lock + sleeps } // condition is true, do work lock.notifyAll(); // wake up ALL waiters }

CONCEPT 3
ReentrantLock — 4 Superpowers
Everything synchronized can’t do. This is what interviewers want you to know.
1. tryLock(timeout)
Try to acquire for N seconds.
Fail? Do something else. Don’t block forever.
synchronized blocks FOREVER.
2. Fairness
new ReentrantLock(true)
Longest-waiting thread goes first.
synchronized has NO fairness guarantee.
3. Multiple Conditions
notFull.await() / notEmpty.signal()
Separate wait-sets per condition.
synchronized has only ONE wait-set.
4. lockInterruptibly()
Waiting thread can be interrupted.
Break out of a deadlock gracefully.
synchronized = uninterruptible.
TEMPLATE — ALWAYS USE TRY-FINALLY
Lock lock = new ReentrantLock(); lock.lock(); try { // critical section } finally { lock.unlock(); // ALWAYS in finally! Else = permanent lock }
⚠ Forget the finally block = lock is held forever. #1 interview mistake.

MUTEX vs SEMAPHORE
🔒 Mutex / Lock
1 thread at a time
Has ownership — only owner unlocks
Reentrant — same thread can re-lock
🎫 Semaphore
N threads at a time
No ownership — anyone can release
Not reentrant — acquire again = -1 permit
💡 Semaphore(1) ≠ Mutex! — No ownership, no reentrancy. Interview trap!

CONCEPT 5
CountDownLatch vs CyclicBarrier
Both make threads wait. But they work completely differently.
CountDownLatch(3)
“I’ll wait until 3 events happen”
Worker 1 → countDown() → 3→2
Worker 2 → countDown() → 2→1
Worker 3 → countDown() → 0 ✅ GO!
Main thread: await()
Released when count hits 0
CyclicBarrier(3)
“ALL 3 of us wait for each other”
Thread 1 → await() → ⏳ waiting…
Thread 2 → await() → ⏳ waiting…
Thread 3 → await() → 💥 ALL GO!
All threads rendezvous
Resets & can be used again!
Feature CountDownLatch CyclicBarrier
Who waits?1 thread awaits, N count downAll N wait for each other
Reusable?No — one shotYes — auto-resets
Action on trip?NoYes — Runnable in constructor
Use caseService startup, test syncPhased computation, gaming
💡 Latch = “gate opens once”  •  Barrier = “everyone arrives, gate opens, repeat”
