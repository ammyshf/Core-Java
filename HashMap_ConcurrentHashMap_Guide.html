What is a HashMap?
The core idea — turning any key into a direct array index
A HashMap stores key-value pairs. Internally it's just an array (called table), where each slot is called a bucket. Given a key, we compute a hash number to find which bucket to store or retrieve from — giving us O(1) average time.
📚
Analogy: Think of a library. Without hashing, you search every shelf one by one = O(n). With hashing, the book's title tells you exactly which shelf to go to = O(1). The hash function is your shelf number calculator.

Internal Node Structure
Each entry is a Node object — key, value, hash, and a pointer to next

Why store hash in the node?
During resize, HashMap must recalculate every node's bucket index. Caching the hash avoids calling hashCode() again for every node — a significant performance optimization.
3
Hashing — From Key to Bucket Index
Three steps: hashCode() → spread bits → bucket index
"Apple"
↓
Step 1: key.hashCode() → 63476538
↓
Step 2: hash = hashCode ^ (hashCode >>> 16) → 63477765
↓
Step 3: index = (16 - 1) & hash → 5
↓
"Apple" goes to Bucket 5
STEP 2 — WHY XOR UPPER BITS?
Spread Function
When table is small (16 buckets), only the last 4 bits of hash decide the bucket. If many keys differ only in upper bits, they'd all collide. XOR'ing with upper bits spreads the influence of all 32 bits into the lower bits.
STEP 3 — WHY & NOT %?
Bitwise AND is faster
(n-1) & hash gives the same result as hash % n when n is a power of 2. But bitwise AND is a single CPU instruction — much faster than modulo division.
// HashMap's actual internal hash function static final int hash(Object key) { int h; return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16); } // Index calculation int index = (table.length - 1) & hash(key);

TREEIFY THRESHOLD = 8
List → Tree
When a bucket has 8 or more nodes AND table length ≥ 64, the linked list converts to a Red-Black Tree. This brings worst-case from O(n) to O(log n).
UNTREEIFY THRESHOLD = 6
Tree → List
During resize, if a tree bucket shrinks to 6 or fewer nodes, it converts back to a linked list. Trees have overhead — not worth it for small buckets.

hashCode() & equals() Contract
The most critical concept — break this and your HashMap silently loses data
THE 3 GOLDEN RULES
1
If a.equals(b) == true → a.hashCode() MUST == b.hashCode()
2
If a.hashCode() == b.hashCode() → a.equals(b) MAY be true or false
3
If you override equals() → you MUST override hashCode()
🏠
Analogy: hashCode() = which street you live on. equals() = which house on that street. Without correct hashCode, HashMap looks on the wrong street. Without correct equals, it knocks on the wrong door.
❌ BROKEN: Override equals() but NOT hashCode()
class Employee { int id; String name; @Override public boolean equals(Object o) { Employee e = (Employee) o; return this.id == e.id; // compare by id } // hashCode() NOT overridden — uses memory address! }
WHAT GOES WRONG
1
e1 = new Employee(1, "Amaan") → hashCode = 12345 (memory)
e2 = new Employee(1, "Amaan") → hashCode = 67890 (different memory!)
2
map.put(e1, "Developer") → hash(12345) → goes to bucket 5
5
e1 : "Developer"
3
map.get(e2) → hash(67890) → goes to bucket 2 → WRONG BUCKET!
2
null — nothing here!
Returns NULL! Data lost forever!
✅ CORRECT: Override BOTH equals() AND hashCode()
class Employee { int id; String name; @Override public boolean equals(Object o) { if (this == o) return true; if (o == null || getClass() != o.getClass()) return false; Employee e = (Employee) o; return id == e.id && Objects.equals(name, e.name); } @Override public int hashCode() { return Objects.hash(id, name); // SAME fields as equals! } }
✅
Now it works!
e1.hashCode() == e2.hashCode() → same bucket → e1.equals(e2) → true → returns "Developer". Use the same fields in both methods. Always.

ConcurrentHashMap Internal Structure (Java 8+)
volatile Node array + CAS + synchronized per bucket head
class ConcurrentHashMap<K,V> { transient volatile Node<K,V>[] table; // volatile = all threads see latest static class Node<K,V> { final int hash; final K key; volatile V val; // volatile for read visibility volatile Node next; // volatile for read visibility } }
CAS (COMPARE-AND-SWAP)
Lock-Free Writes
An atomic CPU instruction: "Set value to X only if current value is still Y". If another thread changed it, CAS fails and the thread retries. Used for empty bucket inserts — no lock needed!
VOLATILE
Lock-Free Reads
volatile guarantees that when Thread 1 writes a value, Thread 2 sees it immediately (no CPU cache staleness). This is why get() needs NO lock at all!

Reads are completely lock-free thanks to volatile

WRITER THREAD

// get() — ENTIRE method is lock-free! public V get(Object key) { int h = spread(key.hashCode()); Node<K,V> e = tabAt(tab, (n-1) & h); // volatile read of bucket while (e != null) { if (e.hash == h && key.equals(e.key)) return e.val; // volatile read of value e = e.next; // volatile read of next pointer } return null; }
⚡
Key Insight
Unlimited readers can call get() at the same time with zero contention. Writers only block other writers on the same bucket. Readers are never blocked by writers.

Interview Quick-Fire Cheat Sheet
Answers to the most commonly asked questions in one glance
HASHMAP INTERNALS
Structure: Array of Nodes (buckets), default 16
Hashing: hashCode() → spread XOR → (n-1) & hash = index
Collision: Linked List → Red-Black Tree at 8 nodes
Resize: When size > capacity × 0.75, double the array
Null key: Allowed (goes to bucket 0). Null value: Allowed
Time: O(1) avg, O(log n) worst (Java 8+). Thread-safe: NO
CONCURRENTHASHMAP INTERNALS
get(): NO lock — uses volatile reads. Unlimited concurrent readers
put() empty bucket: CAS — atomic, no lock
put() collision: synchronized(head node) of that bucket only
Resize: Cooperative — all threads help transfer buckets
ForwardingNode: Marker (hash=MOVED) redirects reads to new table
size(): Distributed counters (baseCount + CounterCells)
Null: NOT allowed (ambiguity in concurrent reads)
HASHCODE & EQUALS CONTRACT
Rule 1: equals() true → hashCode() MUST be same
Rule 2: Same hashCode → equals() MAY be true or false (collision OK)
Rule 3: Override equals() → MUST override hashCode()
Always: Use the same fields in both methods
Break it: Data silently lost in HashMap — put succeeds, get returns null
